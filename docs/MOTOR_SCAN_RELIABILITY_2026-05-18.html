1. 배경

DeepAlign 의 3개 스캔(Mirror / KIMM / ACS) 워커는 모두 mover.move(point) → settle(ms) → snap 루프를 돈다. 각 mover 가 "이동 완료를 어떻게 보장하느냐", "하드웨어 컨트롤러를 어떻게 받느냐", "UI 가 어떻게 생겼느냐"가 제각각이라 신뢰성·일관성에 큰 격차가 있었음.

한 번에 셋 다 같은 수준으로 끌어올리는 게 목표.

Phase 2 — Move-done + Timeout 통합 [d41d65c]

Picomotor: wait_motion_done() 신규 — 8742 SDK에 명시적 motion-done 쿼리 없어 위치 안정성 폴링으로 대체. poll_ms=50 간격으로 GetPosition → 같은 값이 연속 stable_n=3회 관측되면 정지 판정.

def wait_motion_done(self, motor: int, timeout_ms: int = 10000,
                     poll_ms: int = 50, stable_n: int = 3) -> None:
    deadline = time.perf_counter() + timeout_ms / 1000.0
    stable = 0; last = None
    while True:
        ok, pos = self._cmdlib.GetPosition(self._key, self._master, motor, 0)
        if ok:
            if last is not None and pos == last:
                stable += 1
                if stable >= stable_n: return
            else:
                stable = 1
            last = pos
        if time.perf_counter() >= deadline:
            raise TimeoutError(f"Picomotor M{motor} move timeout after {timeout_ms}ms")
        time.sleep(poll_ms / 1000.0)

6. 후속 / 미해결

  • Pico SDK가 MotionDone 쿼리를 실제로 노출한다면 위치 안정성 폴링보다 정확. 추후 SDK 확인 후 교체 가능.
  • PicoCard 폴링(300ms)과 wait_motion_done 내부 폴링(50ms)이 동시 호출돼도 Newport CmdLib8742는 내부 lock으로 안전하지만, 문제 발생 시 PicomotorController에 threading.Lock 추가 권장.
  • 현재 스모크 테스트는 mover 계층까지만 검증. 실제 HW 통합 테스트는 별도 (스캔 시작 → 워커 종료까지의 E2E).
  • Laser (TEUS Server API) 모듈은 별도 — Bearer Token 분기 / endpoint fallback / 잘못된 PUT body 등 결함 존재. 미수정.
